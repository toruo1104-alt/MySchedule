# 構築手順書 — MySchedule フェーズ5(Cloudflare D1+Workers)

本書は MySchedule のバックエンドを Cloudflare Workers + D1 へ移行するための、セットアップ・移行・運用の手順書。
実装の正は `docs/DB設計.md`。

前提: Cloudflare無料アカウント・Node がインストール済み。

---

## 1. 初回構築

```
cd worker
npm install
npx wrangler login
npx wrangler d1 create myschedule-db      # 出力された database_id を wrangler.jsonc に転記
npx wrangler d1 migrations apply DB --remote
```

シークレットを設定する:

```
npx wrangler secret put API_TOKEN
npx wrangler secret put GAS_URL
npx wrangler secret put GAS_TOKEN
```

- `API_TOKEN`: フロントが送る `token` と照合する値(現行の設定シート `apiToken` に相当。UUID等を新規発行してよい)。
- `GAS_URL`: GASプロキシ(`gas/calendar_proxy.gs`)のWebアプリURL(`…/exec`)。
- `GAS_TOKEN`: GASプロキシのScript Propertiesに設定する `PROXY_TOKEN` と同じ値。

デプロイする:

```
npx wrangler deploy
```

- `worker/wrangler.jsonc` の要置換値: `d1_databases[0].database_id`(構築時に置換)。
- D1データベース名は `myschedule-db`(バインディング `DB`)。フロントは Workers Static Assets(`worker/wrangler.jsonc` の `assets.directory="../web"`)で同一オリジン配信される。

## 2. GASプロキシ導入

> **✅ 2026-08-01 実施済み(採用方式)**: 既存GASプロジェクトの置き換えではなく、**プロキシ専用の新規GASプロジェクト**(script.new)を作成する方式を採用した。旧GAS(スプレッドシート版API)は無傷で残るためロールバック保険が維持され、カットオーバー前でも週ビュー・取込が使える。旧GASプロジェクトはカットオーバー完了後にアーカイブ(無効化)すればよい。⚠ script.new は**予定が入っているGoogleアカウント(toruo1104)でログインしたブラウザ**で開くこと(別アカウントで作ると自分のカレンダーが空に見える事故が起きる。実際に起きた)。

既存GASプロジェクト(現行 `コード.gs`)を置き換える場合の手順(参考。上記の新規プロジェクト方式なら同じ内容を新規プロジェクトに貼る):

> ※ 置換方式を採る場合は、既存アプリ(スプレッドシート版)のカットオーバー後に行うこと。カットオーバー前に置き換えると、既存のスプレッドシート版APIが停止し、旧フロント(GitHub Pages)からデータ操作ができなくなる。

1. `gas/calendar_proxy.gs` の内容を、既存GASプロジェクトのコードへ置換する(コードエディタで貼り替え)。
2. `appsscript.json` は `gas/appsscript.json` の内容で置き換える(Tasks高度なサービスの宣言を含む)。GASエディタの「サービス」からTasksを有効化済みの場合も、貼り替え後にTasksが有効なことを確認する。
3. GASエディタ → プロジェクトの設定 → スクリプト プロパティ で `PROXY_TOKEN` を設定する(worker側の `GAS_TOKEN` と同じ値)。
4. デプロイ → **新しいバージョンとしてデプロイ**(既存のWebアプリURLを維持するため「デプロイを管理」から更新)。
5. WorkerのSecret `GAS_URL` に、このGASプロキシのWebアプリURLを設定する(§1参照)。

## 3. データ移行

既存のスプレッドシート版から移行する手順。**カットオーバー前(旧アプリ稼働中)に実施してよい**(読み取り専用のエクスポートのため)。

1. `scripts/export_for_db.gs` を既存GASプロジェクトに一時的に貼り付け → `exportForDb` を実行 → マイドライブにJSONファイルが出力される(実行ログに各シートの件数が出る)。シートは変更しない(読み取り専用)。
2. ダウンロードしたJSONを **`scripts/out/` 配下**に保存し(例: `scripts/out/myschedule-export.json`)、SQLに変換する。

   ```
   node scripts/json_to_sql.mjs ./scripts/out/myschedule-export.json
   ```

   出力先は `scripts/out/seed.sql` に固定(標準出力の件数サマリと警告を確認する)。

   > ⚠ **リポジトリ直下や他の場所に置かない。** `scripts/out/` と `myschedule-export*.json` はgitignore済みだが、置き場所を固定して事故を防ぐ。

3. まず **`--local`** に試験投入する。

   ```
   cd worker
   npx wrangler d1 execute DB --local --file=../scripts/out/seed.sql
   npx wrangler d1 execute DB --local --file=../scripts/verify_migration.sql
   ```

   `days` の行数・`json_each` によるスロット総数一致・`json_valid` 全件・各テーブル件数を確認し、手順1でGASの実行ログに出た件数と突き合わせる。サンプル数件は目視で内容も確認する。

4. 問題なければ `--remote` へ投入する。**投入の直前**にバックアップを取る。

   ```
   npx wrangler d1 export DB --remote --output=./scripts/out/backup_before_seed.sql
   npx wrangler d1 execute DB --remote --file=../scripts/out/seed.sql
   npx wrangler d1 execute DB --remote --file=../scripts/verify_migration.sql
   ```

   検証内容は手順3と同様(`--remote` で再実行)。

> ⚠ **データファイル(exportしたJSON・`scripts/out/seed.sql` 等)はPublicリポに絶対にコミットしない。** MyScheduleリポジトリは無料GitHub Pagesの条件でPublicであり、個人のスケジュールデータそのものが漏洩する。`scripts/out/` は `.gitignore` 対象とし、手元でのみ扱うこと。

> ⚠ **`seed.sql` は全テーブルDELETE後の全置換。初回移行専用。** カットオーバー後に再実行すると、移行後に入力した予定がすべて消える。

## 4. ローカル開発

```
cd worker
npx wrangler d1 migrations apply DB --local
npx wrangler dev --local          # http://localhost:8787 でフロントごと動く
```

- ローカル専用の環境変数は `.dev.vars` に記述する(例: `API_TOKEN`/`GAS_URL`/`GAS_TOKEN` のローカル用の値)。**`.dev.vars` はgit管理対象外**(`.gitignore` 済み)。
- `wrangler.jsonc` の `vars` にはローカル専用値・シークレットを書かない(secretは `wrangler secret put` で本番に個別設定する)。
- `worker/test/smoke.mjs` は冒頭でローカルD1の `days`/`categories`/`import_map` を初期状態にリセットする。移行リハーサル等の検証データを守る場合は `--persist-to` でディレクトリを分けること。

## 5. 運用

- バックアップ:

  ```
  npx wrangler d1 export DB --remote --output=./scripts/out/backup.sql
  ```

  任意タイミングでの実行に加え、D1 Time Travel による誤操作からの復元が利用できる。

- 管理画面(スプレッドシート直接編集)の代替: Cloudflareダッシュボード → D1 → `myschedule-db` → Console での定型SQL実行。

  - 区分の確認:
    ```sql
    SELECT * FROM categories ORDER BY sort;
    ```
  - ある日のスロット内容確認:
    ```sql
    SELECT * FROM days WHERE date='2026-08-01';
    ```
  - 設定値の確認:
    ```sql
    SELECT * FROM config;
    ```

## 6. カットオーバー手順

> **✅ 2026-08-02 実施済み。**

Workerのデプロイは**ローカル作業ツリーから** `npx wrangler deploy` で行うため、**mainへのマージ前に本番Workerを立てて並行稼働できる**(旧GitHub Pages+旧GASはそのまま生きている)。推奨順序は次のとおり。

1. `phase5-db` の作業ツリーから `npx wrangler deploy` してWorkerを立て、Worker URL(`*.workers.dev`)で数日並行運用する(旧アプリ・旧GAS APIは無停止のまま)。Worker URLで開いた画面の設定モーダル(⚙)にはAPI URL(`https://…workers.dev/api`)が自動プリセットされるので、`API_TOKEN` の値を入力して保存すれば接続できる。
2. 問題なければ `phase5-db` を `main` にマージ&push する。

   > ⚠ **この時点で旧Pages URLは404になる。** ルートの `index.html` が `web/` へ移動したため。以後は Worker URL がアプリの正。

3. GASプロキシへ置換する(旧データAPIが停止する。§2参照)。
4. `GAS.txt`・`appsscript_json.txt` を削除するコミットを行い、GitHub Pagesを無効化する(リポジトリ設定 → Pages)。

---

## 7. ロールバック

- **カットオーバー後の切り戻しは不可**(旧GASのデータAPI・GitHub Pagesは退役済み)。データ保全はD1バックアップ(§5)とD1 Time Travelで行う。
- 既存スプレッドシートは移行後も**読み取り専用のまま温存**している(削除しない)。
- 参考: カットオーバー前(§6 手順1の並行運用期間)は、フロントの設定モーダルで旧GAS APIのURLへ戻すことでスプレッドシート版へ切り戻せた(旧GASのWebアプリを停止していない限り)。GASプロキシへの置換(§2)を行うと旧データAPIは停止するため、切り戻しが必要な期間は置換を遅らせる、または旧コードを別デプロイとして残しておく、という判断が必要だった。
